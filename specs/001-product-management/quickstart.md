# 퀵스타트 (Quickstart): 커머스 상품 관리

**날짜**: 2026-10-07 | **계획**: [plan.md](./plan.md) | **계약**: [product-api.openapi.yaml](./contracts/product-api.openapi.yaml) | **데이터 모델**: [data-model.md](./data-model.md)

이 문서는 기능이 처음부터 끝까지 동작하는지 확인하는 검증 시나리오다. 구현 코드는 포함하지 않는다.

## 사전 준비

- Docker(PostgreSQL, Testcontainers, `full` 프로필용). 방식 A에는 JDK 21과 Node.js 22 이상도 필요하다
- 저장소 루트에서 `backend/`, `frontend/`, `docker-compose.yml`이 있어야 한다(구현 이후)
- `.env.example`을 `.env`로 복사하고 값을 채운다(`.env`는 커밋하지 않는다)

## 실행

### 방식 A: DB만 Docker, 앱은 로컬 실행 (기본, 일상 개발)

```bash
# 1. 데이터베이스 시작
docker compose up -d postgres

# 2. 백엔드 실행 (개발 프로필: 인메모리 운영자 계정과 샘플 카테고리 사용)
#    .env의 값을 환경 변수로 읽어 들인 뒤 실행한다(Git Bash).
set -a; source .env; set +a
cd backend && SPRING_PROFILES_ACTIVE=dev ./gradlew bootRun

# 3. 프런트엔드 실행 (다른 터미널)
cd frontend && npm install && npm run dev        # http://localhost:5173
```

### 방식 B: 전체를 Docker로 실행 (`full` 프로필, 온보딩·통합 확인)

```bash
docker compose --profile full up --build   # 프런트엔드 http://localhost:5173, 백엔드 http://localhost:8080
# 종료: docker compose --profile full down   (데이터까지 삭제: down -v)
```

8080 포트가 이미 사용 중이면 백엔드를 `SERVER_PORT=18080`으로 실행하고, 프런트엔드는
`API_PROXY_TARGET=http://localhost:18080 npm run dev`로 시작한다. `full` 프로필은 `.env`의 `BACKEND_PORT`,
`FRONTEND_PORT`로 호스트 포트를 바꾼다. `full` 프로필은 개발 전용이며 프런트엔드 번들에 개발용 운영자 계정이 포함된다.

개발 프로필의 운영자 계정과 비밀번호는 `.env`의 환경 변수로 주입한다. 저장소에 커밋하지 않는다.
업로드된 이미지는 `full` 프로필에서 이름 있는 볼륨에 보존된다.

## 자동 검증

```bash
cd backend && ./gradlew check        # 포맷·정적 분석 + 단위·통합·계약 테스트
cd frontend && npm run lint && npm test && npm run test:e2e
```

## 검증 시나리오

각 시나리오는 명세의 인수 시나리오와 성공 기준에 대응한다. 모든 시나리오는 `PRODUCT_MANAGER`
권한으로 수행한다.

| # | 시나리오 | 기대 결과 | 근거 |
|---|----------|-----------|------|
| 1 | 상품명·가격·카테고리를 입력하고 등록 | 201, 코드가 `PRD-`로 자동 생성되고 목록에 나타남 | US1, FR-001, FR-005 |
| 2 | 필수 항목을 비우고 저장 | 400, 누락된 항목이 `errors`에 표시됨 | US1, FR-003, SC-005 |
| 3 | 가격 0, 재고 -1 입력 | 400, 저장되지 않음 | FR-004, SC-005 |
| 4 | 이미 있는 코드를 직접 입력해 등록 | 409, 중복 안내 | FR-005 |
| 5 | 옵션(색상×사이즈)과 조합별 재고로 등록 | 모든 조합이 저장되고 같은 조합 중복은 400 | FR-015 |
| 6 | PNG 11장째 업로드, 6MB 파일, GIF 업로드 | 각각 400/413/400으로 거부, 사유 안내 | FR-002 |
| 6-1 | 이미지 없이 상품 등록, 대표 이미지 삭제 | 등록 성공, 대표 삭제 시 남은 첫 이미지가 자동으로 대표가 됨 | FR-002 |
| 7 | 모든 조합 재고를 0으로 수정 | 상태가 `SOLD_OUT`으로 바뀜 | FR-009, FR-016 |
| 8 | 품절 상품의 재고를 1 이상으로 보충 | 상태가 `ON_SALE`로 자동 복귀 | FR-009 |
| 9 | `HIDDEN` 상품의 재고를 보충 | 상태가 `HIDDEN`으로 유지됨 | FR-008, FR-009 |
| 10 | 두 클라이언트가 같은 버전으로 수정 후 차례로 저장 | 첫 저장 200, 두 번째 저장 409 | FR-007 |
| 11 | 상품명 일부·카테고리·상태로 검색, 정렬, 페이지 이동 | 조건에 맞는 상품만 반환, 결과 없으면 빈 목록 | US3, FR-010, FR-011 |
| 12 | 상품 1만 개 적재 후 검색 | p95 1초 미만(목표 5초 이내) | SC-002 |
| 13 | 상품 삭제 후 목록·상세 조회 | 목록에서 사라지고 상세는 404, DB에는 `deleted_at`이 기록됨 | US4, FR-012 |
| 14 | 주문 이력이 있는 상품(테스트용 참조 데이터) 삭제 | 삭제되어도 과거 참조 데이터는 보존됨 | FR-012, SC-006 |
| 15 | 생성·수정·삭제 후 변경 이력 확인 | 변경자·시각·내용이 각 1건씩 기록됨 | FR-013 |
| 16 | 인증 없이, 또는 다른 역할로 운영자 API 호출 | 각각 401, 403 | FR-014 |
| 17 | 인증 없이 고객 조회 API 호출 (판매중·품절·숨김·삭제 상품 혼재) | 판매중·품절만 목록에 나타나고 재고 수량은 없이 `soldOut`만 표시, 숨김·삭제 상품 상세는 404 | FR-008, FR-012, FR-018 |
| 18 | 상품 가격 수정 직후 고객 조회 API 호출 | 수정 내용이 즉시(1분 이내) 반영됨 | SC-003 |
